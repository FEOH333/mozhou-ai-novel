# V0.100.7 自动创作 Agent / Harness 框架评估与落地结论

首次评估：2026-08-24；复核：2026-08-28

## 结论

V0.100.7 仍不把 DSH、Pi、LangGraph、Mastra 或 OpenAI Agents SDK 作为运行时依赖嵌入墨舟，也不并行保留多套自动创作编排器；这一结论是在重新核对各项目官方资料并完成正文质量、返工状态与弱网恢复审计后作出的，不是因为框架“没用”。

这不是否定 harness 的价值，而是区分两件事：

- harness 擅长把“观察—规划—调用工具—检查结果—继续/停止”组织得更可靠；
- 小说是否好看，主要仍取决于模型能力、输入材料、创作纪律、正文证据、候选比较和落盘门禁。换一个 agent loop 不会自动把水文变成合格正文。

墨舟已经拥有书级租约、章节状态机、SQLite 检查点、SSE 事件、失败关闭、恢复快照、模型路由、缓存分层、写审同源与正文落盘闸门。V0.100.7 又补齐了服务端后台作业所有权、断线事件重放、显式取消、严格候选来源契约、全范围因果修复计划和滚动预期新稿。审计找到的首要瓶颈是“正文提示膨胀和配方化”“正文换版后派生状态仍是旧版”以及“局部候选被误当作可跨轮的整体方案”，不是缺少一个能循环调用工具的 Agent 外壳。再引入通用 harness，会同时出现两套状态、两套重试、两套工具协议和两套可观测链路；复杂度与回归面大于当前收益。

| [Mastra Agents / Workflows](https://mastra.ai/docs/agents/overview) | Agent 适合开放式未知步骤，Workflow 适合预定义控制流 | 墨舟恰好属于预定义、强约束 workflow；现有实现已承担该角色，引入会形成第二套工作流事实源 | 不引入 |
| [OpenAI Agents SDK for JavaScript](https://openai.github.io/openai-agents-js/) | Agent、handoff、session、guardrail、trace 等通用能力 | 当前服务兼容多种 OpenAI/Anthropic/DeepSeek 风格端点，并有自有计价、缓存和重试。接入会扩大供应商耦合与会话状态面 | 吸收 session/guardrail/trace 思路，不引入 |

## 小说创作项目与研究的参考价值

- [NovelClaw](https://github.com/iLearn-Lab/NovelClaw) 和 [OpenNovel](https://github.com/Yaemikoreal/OpenNovel) 说明长篇创作需要规划、记忆、检索、审阅与持续状态，而不是一次超长提示；墨舟保留自己的本地 SQLite 管线，避免为了对齐别人的数据模型迁移现有作品。
- [CONCOCT](https://arxiv.org/abs/2311.04459) 与 [DOME](https://arxiv.org/abs/2412.13575) 等长文本研究强化了分层规划、迭代展开和多层评估的价值；它们提供方法启发，不构成“换上论文方法就必然写好网文”的承诺。
- [Lost in the Middle](https://arxiv.org/abs/2307.03172) 与 Anthropic 的[上下文工程实践](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)共同支持一个工程判断：上下文窗口能装下更多内容，不等于模型能同等有效地使用所有内容。因此 V0.100 把正文任务改为有界上下文，把全局审阅留在独立任务中。

## V0.100.7 实际吸收的 Harness 思想

不引入依赖，但把有用的编排思想落在现有单一管线上：

1. `observe`：平台审核状态、剩余次数、公开发布边界和作品数据作为动态事实；创作前同时读取当前叙事版本、正文指纹和经验证经验。
2. `bounded context`：正文模型只拿固定材料、最近两章全文和当前章前置场景；审阅模型另走隔离全局上下文。上下文选择成为显式规划器，不再让历史堆无限生长。
3. `plan`：章纲先产生可校验的戏剧契约；推荐恢复再按五章批次生成 1—20 章质量曲线。所有诊断必须引用原文，章号分段只是审查先验。
4. `shadow act`：返工候选不直接覆盖正文；先在 shadow revision 中为所有完成章建立摘要、事实、人物、时间线、伏笔、记忆和实际章纲投影。
5. `independent verify`：候选先过长度、完整性、重复与 AI 模板腔确定性闸，再做 A/B 双向换位盲审；严格正文证据门禁止模型把不存在的剧情写进数据库。
6. `global verify`：关键章候选齐备后，做 1—20 章整段因果复核；随后独立校准书纲、卷纲、未来章种子和设置。任一步失败都不切换旧稿。
7. `checkpoint and replay`：每个有效版本保存父版本、正文指纹、逐章投影、变更清单与跨层对账结果；返工后台作业独立于浏览器连接，断线后按作业 id 重放事件，只有显式停止才取消。候选检查点分为本运行局部通过、整段通过和整段否决，不能混用。
8. `verified learning`：恢复经验先处于 provisional；只有证据诊断、确定性改善、双向盲审和整体复核全部通过才激活。经验是正向目标，带置信度、章节作用域和使用次数，不把旧坏句或失败模型意见塞回提示。
9. `provenance contract`：跨运行候选复用必须同时匹配契约版本、诊断指纹、完整工单、当前章正文、相邻章接口，并且来源候选已通过整段复核；局部候选只能在同一次运行中断点续跑。
10. `whole-range plan`：五章批次只采集证据，最终由全范围综合计划建立跨章故事弧、依赖、保护事实和交接责任；候选按拓扑顺序生成，后章读取前章已接受候选形成的预期新稿。

这套实现把 harness 用在“限制上下文、阻止未经验证的状态落盘、让版本可回放、让经验有准入门槛”上，而不是用 Agent 数量制造虚假的质量提升。

## 何时重新评估

只有出现以下真实需求，才重新做小型分支验证，不直接全量迁移：

- 自动创作出现大量运行时未知、必须让模型动态发现并选择工具的步骤；
- 需要跨进程/跨机器恢复长达数小时的多角色任务，而现有 SQLite 检查点不足；
- 需要多个不同供应商、不同提示词的独立审稿代理并行运行，且离线基准证明比当前双向盲审稳定；
- 现有状态机、租约或事件追踪成为可测量的主要开发瓶颈，而不是正文质量或模型能力成为瓶颈。

重新评估时必须用同一批真实章节做基线对照：比较有效事件密度、证据可定位率、候选安全门通过率、人工盲读结论、调用成本和失败恢复，不接受“框架更流行”或“agent 更多”作为迁移理由。

## 对当前失败的判断

签约审核曾通过，只能给“前五六章可能勉强可用”一个弱先验，不能证明它们优秀。推荐评估查看更长的前段内容后拒绝进入验证，更符合“正文质量曲线在后续持续下坠”的解释。楔子能力和模型能力都可能有缺陷，但楔子本身不可能替第 7—20 章的空转、重复商议、回报拖延和缺少后果偿债。因此 V0.99 的主修方向是整段质量恢复闭环，而不是继续堆楔子或换一个通用 agent 外壳。
